Every asset is a single Markdown file on disk under `~/.chain-hub/`.

## The five kinds

| Kind | File path | Synced to editors |
| --- | --- | --- |
| `skills` | `skills/<name>/SKILL.md` | Claude Code, Cursor, Windsurf, Devin CLI, Zed, Antigravity |
| `agents` | `agents/<name>.md` | Claude Code, Devin CLI, Antigravity |
| `workflows` | `workflows/<name>.md` | Windsurf, Devin CLI |
| `rules` | `rules/<name>.md` | Claude Code, Cursor, Windsurf, Devin CLI, Zed, Antigravity |
| `prompts` | `prompts/<name>.md` | none — library-only |

Skills are the only kind that live in their own folder (`skills/<name>/SKILL.md`
instead of `skills/<name>.md`), so a skill can ship supporting files
alongside it later.

## Skills need a description

Editors like Zed reject skills without a non-empty `description`. Give every
skill frontmatter with at least a description:

```md
---
description: Reviews pull requests for common correctness issues.
---

# PR Review

Check for unhandled errors, missing tests, and unclear naming before approving.
```

Writing a skill without a description fails with:

```
Skill description is missing. Editors like Zed reject skills without a non-empty description.
```

Agents, workflows, rules, and prompts don't require frontmatter — plain
Markdown is a valid asset. The seeded welcome skill is a real example with
no frontmatter at all:

```md
# Welcome

You are inside Chain Hub v2.

- Keep AI guidance local and portable
- Prefer clear workflows over hidden magic
- Validate changes before syncing into editors
```

## Frontmatter fields

Frontmatter is optional everywhere except the skill `description`, and it's
preserved verbatim when assets project into editors — editor-specific
defaults (Cursor's `alwaysApply`, Antigravity's `trigger: always_on`) only
fill fields you leave unset. The fields each editor actually honors:

| Kind | Field | Type | Used for |
| --- | --- | --- | --- |
| `skills` | `description` | string | Required for Zed and other strict editors; shown in pickers |
| `skills` | `allowed-tools` | list | Tool allowlist (Claude Code style) |
| `skills` | `triggers` | list | e.g. `triggers: [user]` — Devin CLI workflow-skills invocable as `/name` |
| `skills` | `license` | string | Packaged skills conventionally carry one |
| `skills` | `metadata` | map | Free-form; `metadata.author` powers author search in the Library |
| `agents` | `tools` | list | Claude Code subagent tool list (dropped on Antigravity) |
| `agents` | `model` | string | Claude Code subagent model (`sonnet`, `haiku`, …) — dropped on Antigravity |
| `rules` | `globs` | list | Makes the rule a glob-scoped rule in editors that support it |
| `rules` | `alwaysApply` / `trigger` | — | Editor activation mode; adapters default it when absent |
| all | `author` | string | Shown wherever the asset appears (see below) |

Unknown fields aren't stripped — they round-trip through the hub and land in
the projected file, so editor features we haven't mapped still work.

## Creating an asset

```bash
chain asset create --kind skills --name pr-review --content "$(cat pr-review.md)"
chain asset show --kind skills --name pr-review
chain asset update --kind skills --name pr-review --content "$(cat pr-review.md)"
chain asset remove --kind skills --name pr-review
```

Or use the dashboard's **Library** page — same operations, visual editor.

## Author field

An optional `author` frontmatter field is read and shown wherever the asset
appears. Skills installed from an upstream source are marked
upstream-owned; editing one directly fails with:

```
Skill skills/<name> is upstream-owned. Fork it to customize, or edits will be lost on update.
```

Fork it first, then edit the fork.
